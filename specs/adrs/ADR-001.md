# ADR-001: Authentication Architecture Decisions

## Context

PRD-001 defines requirements for a User Authentication system covering registration, login, session management, and brute-force protection. Several architectural decisions must be made to implement these requirements securely and maintainably.

---

## Decision 1: Password Hashing — bcrypt

### Status
Accepted

### Context
Passwords must be stored securely. The PRD mandates a hashing algorithm that resists brute-force and rainbow table attacks (FR-1, NFR: salt rounds ≥ 12).

### Decision
Use **bcrypt** with a minimum of **12 salt rounds** for all password hashing.

### Alternatives Considered
| Option | Reason Rejected |
|---|---|
| MD5 / SHA-256 | Not designed for passwords; vulnerable to brute-force |
| Argon2 | Stronger, but bcrypt is widely supported and meets NFR requirements |
| PBKDF2 | Acceptable, but bcrypt is idiomatic for Node.js ecosystem |

### Consequences
- Password comparison will add ~100–300ms latency (acceptable; login target < 500ms p95)
- CPU-intensive on high load — consider async bcrypt calls to avoid blocking the event loop

## Decision 2: Session Storage — HTTP-only Cookies

### Status
Accepted

### Context
Sessions must persist across requests and support "Remember Me" duration variants (FR-3). The storage mechanism must be resistant to XSS token theft.

### Decision
Store session tokens in **HTTP-only, Secure, SameSite=Strict cookies**.

- Default session: **24 hours**
- "Remember Me" session: **30 days**

### Alternatives Considered
| Option | Reason Rejected |
|---|---|
| localStorage / sessionStorage | Accessible via JavaScript — vulnerable to XSS |
| JWT in Authorization header | Requires client-side storage; no built-in revocation |
| In-memory (server-side only) | No persistence across server restarts |

### Consequences
- CSRF protection required (mitigated by `SameSite=Strict`)
- Session revocation is straightforward via server-side session store
- Cookies must be transmitted over HTTPS only (`Secure` flag)

## Decision 3: Rate Limiting Strategy — Per-IP, In-Process (with upgrade path)

### Status
Accepted

### Context
FR-4 requires: max 5 failed login attempts per minute per IP, and account lock after 10 consecutive failures. The system must protect against brute-force without locking out legitimate users.

### Decision
Implement **two-layer rate limiting**:

1. **IP-based rate limit**: 5 failed attempts / minute using an in-process sliding window (e.g., `express-rate-limit`)
2. **Account-level soft lock**: after 10 consecutive failures, temporarily lock the account for a fixed cooldown period (e.g., 15 minutes)

For MVP, use in-process counters. The design should support migrating to a Redis-backed store (e.g., `rate-limit-redis`) for horizontal scaling.

### Alternatives Considered
| Option | Reason Rejected |
|---|---|
| Permanent account lock | Risk of denial-of-service against legitimate users (< 1% false lockout NFR) |
| CAPTCHA only | Adds UX friction; does not enforce hard limits |
| Redis from day one | Adds infrastructure dependency; unnecessary for initial scale |

### Consequences
- In-process counters reset on server restart — acceptable for MVP
- Must track both IP and account-level failure counts independently
- Account lock must surface a clear user-facing message distinct from "Invalid credentials"

## Decision 4: Error Message Strategy — Generic Credential Errors

### Status
Accepted

### Context
FR-2 requires showing "Invalid email or password" on failed login. This prevents user enumeration attacks where an attacker could distinguish between "email not found" and "wrong password".

### Decision
Return a **single generic error message** — `"Invalid email or password"` — for all credential failures, regardless of whether the email exists or the password is wrong.

### Consequences
- Slightly reduced UX clarity (user cannot tell if they mistyped email vs. password)
- Eliminates account enumeration via login endpoint
- Registration endpoint must separately enforce unique email (FR-1) with an appropriate message

---

## Decision 5: Out-of-Scope Deferral — OAuth, 2FA, Password Reset

### Status
Accepted

### Context
The PRD explicitly marks OAuth/Social login, 2FA, and password reset as out of scope for this iteration.

### Decision
These features will **not** be implemented in this phase. The authentication system will be designed to allow future extension (e.g., provider abstraction layer) without requiring structural changes.

### Consequences
- No external OAuth dependencies in MVP
- Users cannot recover accounts if passwords are forgotten — acceptable for current phase
- Architecture should not tightly couple session management to a single-factor flow
